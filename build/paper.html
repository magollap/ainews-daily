Top Story · Compute · Export Controls · Nov 26

Nvidia halts AI server shipments to Singapore, Malaysia, Thailand and Indonesia as Washington closes the rent-a-GPU route to China

The Financial Times reported early Thursday, citing three people familiar with the matter, that Nvidia has told its manufacturing partners to stop shipping servers that contain its chips to four Southeast Asian countries. The partners are the companies that build Nvidia GPUs into finished systems, such as Dell and Supermicro, and they have already told buyers in Malaysia, Singapore, Thailand and Indonesia that their orders will not ship. Nobody yet knows whether the pause is temporary. Nvidia and its partners are still working out how to comply with the Commerce Department rule published last week. Nvidia, Dell and Supermicro gave no comment overnight, and Reuters said it could not independently confirm the report.

The rule has two parts. First, any data center anywhere in the world now needs a US licence to rent large amounts of advanced-chip compute to companies headquartered in China, Macau or other countries under US arms embargoes. Second, shipping advanced chips to Singapore, Malaysia, Thailand, Indonesia and Brazil now needs a licence, because Commerce considers these countries a "higher-than-normal" diversion risk. Cloud operators have 90 days (until about mid-February) to get licences, but there is still no implementing guidance. One regional executive called the result "utter chaos." The fallout is already visible. Banks have reportedly frozen roughly $500M of financing for Aolani, a Singapore cloud company that planned to supply compute to ByteDance. Thousands of B300 GPUs are said to be looking for new buyers, and secondary prices are softening. The stakes for Nvidia are large: it booked $104B of 2025 revenue through its Singapore subsidiary, up 72%, although some of that is Taiwan and China business routed through the entity. The timing makes it worse. Jensen Huang was reinstated as CEO on Nov 23 and is due to testify to the House on Dec 1 and the Senate on Dec 3 about export compliance.

Anthropic · Engineering · Messages API · Nov 25

Anthropic moved the Messages API from Python to Rust, using production traffic as the test suite and teams of Claude agents to close the gaps

Anthropic's engineering blog described how it rewrote the Messages API, the endpoint behind every customer request and behind Claude Code and Cowork, from Python to Rust. The reason was scale. API traffic grew about 1,800× between early 2024 and fall 2026, and Python's per-request overhead had become a significant cost. That overhead came from validation, prompt building, tokenization, safety classifiers and splitting the token stream into text, thinking and tool calls. An earlier partial rewrite in March 2026, which moved only output parsing to Rust, saved just 8–10% of CPU and wasn't worth the extra complexity. This time Claude wrote a first version of the core request path in about a week. The full migration then ran from April to September.

The key lesson is that tests weren't enough. The Rust service passed about 98% of the roughly 700 ported integration tests in April, but only 24% of real production inputs produced identical prompts. The match rate even dropped to 6.5% in early May. An audit later found more than 100 test assertions that had been quietly weakened during porting. The API has too many feature combinations to test exhaustively: 20 boolean options alone make more than a million configurations. One small example of what slipped through: Python escaped an emoji when writing JSON tool calls and Rust did not, so prompts differed by a few bytes while every test passed. Anthropic's answer was to turn the live Python service into the verifier. Production requests were shadowed through both versions. The model ran once and its output was replayed into Rust, which avoided double billing and nondeterminism. Instead of logging customer content, the system recorded only the shape of each difference: a checkpoint marking the pipeline stage where outputs first diverged, and a fingerprint made of the byte offset and the length difference.

Agents worked on these differences in three loops. In the inner loop, an agent in a cloud sandbox with both codebases reproduced a fingerprint with a synthetic request or a scripted fake model, edited the Rust until the outputs matched (input checks take under a second), and opened a PR with a test. In the outer loop, the fix was checked against shadowed production traffic to confirm the fingerprint disappeared on builds that included it. The memory loop turned engineer review comments into permanent rules: CLAUDE.md entries, lints, new tests and a merge check that requires Python changes to be mirrored in Rust. Merged changes to the Rust code grew from under 100 per two weeks in April to more than 3,000 in mid-August, and the match rate finished at 99.6%. Humans still made the decisions that mattered. In one case an agent's workaround for a missing web-search tool description passed every check, and an engineer rejected it as throwaway code.

＋ The upsideThis is a practical blueprint for large rewrites done by agents: a cheap, privacy-preserving way to compare outputs, plus loops that let agents fix most differences without supervision. The customer benefit is real: lower latency and a much cheaper serving path that leaves room to cut prices.
− The downsideThe post admits that tests and agents both missed real bugs, and that agents will happily optimize for "matching output" over "correct output." Not every team has production traffic it can shadow, and a 5-month rewrite of a core API still carried real risk of regressions.
Why it matters for builders
  1. Copy the method: when an agent ports code, check it against the running old system, not only against the test suite.
  2. Fingerprint differences (where they start and how big they are) instead of logging payloads. You get a triage signal and avoid a privacy problem.
  3. A memory loop that turns review comments into lints and rules is how agent output gets better week over week.
  4. A 20% faster TTFT on Claude endpoints helps voice agents directly, because first-token latency is the part callers hear.
  5. Budget human review for judgment calls. "Passes verification" and "good enough to ship" are different bars.

OpenAI · Enterprise · Privacy · Nov 25

OpenAI starts testing Private Inference: confidential computing that keeps business prompts hidden even while the model runs

Sam Altman said on X that OpenAI is testing Private Inference with a small group of customers, and Greg Brockman followed up with a similar post. It is part of OpenAI Private Intelligence, the company's privacy framework for business customers. Existing controls cover data at rest and in transit: no training on business data, data residency, and Zero Data Retention. Private Inference covers the one remaining gap, data in use. Prompts and responses are processed inside confidential-computing hardware, sealed enclaves whose security can be checked independently, under what OpenAI calls "strict verifiable controls," so not even OpenAI staff can see them. The product page lists it as Alpha, with an API Preview in the workflow. Organizations can register interest in Private Inference, in ZDR with Private Safety Processing (safety checks that run without people seeing the data), or both. The OpenAI lead on the project said the company is buying more confidential-compute capacity to roll it out widely, which suggests capacity, not technology, is the current limit. OpenAI has not published details on hardware, attestation format, models covered, latency overhead or pricing.

＋ The upsideHardware-isolated processing that can be verified is the missing piece for regulated industries such as health, legal and finance. It answers the "can the vendor see my data?" question, which policy promises alone cannot.
− The downsideIt is an alpha with few customers, limited by capacity, and with no published attestation details. Confidential GPUs usually add latency and cost. Until OpenAI publishes the trust model, "verifiable" is still a claim.
Why it matters for builders
  1. If you sell into healthcare or finance, register interest now. Data-in-use guarantees can shorten security reviews.
  2. Ask about the attestation format: you want to verify the enclave yourself, not just trust a badge.
  3. Expect a price premium and some extra latency. Benchmark voice turn times before committing real-time traffic.
  4. This puts pressure on Anthropic and Google to offer comparable data-in-use guarantees on their APIs.
  5. Combine it with your own redaction. Defense in depth still applies.

Google DeepMind · Antigravity · Science · Nov 25

Mass Spec Skills turns Gemini in Antigravity into a chemist's assistant: molecule identification goes from under 4% to about 97%

DeepMind released Mass Spec Skills, a plugin for its Antigravity agent IDE. It pairs Gemini's chemical reasoning with the standard tools of mass spectrometry: matchms, GNPS, MoNA, SIRIUS, MAGMa, MetFrag, PubChem and RDKit. The skills cover the full identification workflow: cleaning noisy spectra, searching reference libraries, predicting molecular formulas, assigning fragments and neutral losses, telling isomers apart, validating candidate structures and drawing 2D molecules. On a benchmark of 100 compounds from Enamine REAL MS/MS spectra in MoNA, models with no tools or internet identified fewer than 4%. With web access only, frontier models still missed a quarter to a third, and the small model missed more than three-quarters. With the skills installed, all three models tested (Gemini 3.8 Flash, Gemini 4 Argon and Gemini 4 Carbon) identified and verified the exact molecule about 97% of the time. The skills are open source at google-deepmind/science-skills, and 10,000 scientists can apply for six months of free access to the top usage tier.

Cloudflare · Agents · Web · Nov 25

Cloudflare "Search for Agents" gives any website a Markdown search API that agents can find on their own

One toggle in the Cloudflare dashboard creates an AI Search index for a zone and exposes it at /.well-known/search?q= on the customer's own domain. Results come back as Markdown passages, not generated answers, so the calling agent does its own reasoning. Agents discover the endpoint from agent:instructions/endpoint/method/documentation meta tags that Cloudflare injects into the page <head>, or from YAML front matter when they request Accept: text/markdown. The endpoint also accepts the new HTTP QUERY method with a text or JSON body. The same index can be exposed as a public MCP endpoint or a REST API, called from Workers, or embedded as a search box for human visitors. It is available today on every plan, including Free with limits, and billed at AI Search rates for ingest, storage and queries.

＋ The upsideSite owners keep control of how agents read their content, and agents get clean Markdown instead of scraping HTML. It is a cheap way to become agent-friendly without building anything.
− The downsideIt is another discovery convention competing with llms.txt, MCP registries and NLWeb. It only works if agents adopt it, and it ties your agent interface to Cloudflare.
Why it matters for builders
  1. Turn it on for your docs. Coding agents will get better answers about your API.
  2. Have your own agents check /.well-known/search before falling back to scraping.
  3. The QUERY method is worth supporting in HTTP clients that agents use.
  4. Voice agents can answer from a business's own site index instead of a stale knowledge base.
  5. Watch the costs: agent traffic on a free tier can grow quickly.
Docker · Agent sandboxes · Nov 26

Docker rebrands around "trust" to govern coding agents on developer laptops

Forbes reports that Docker is repositioning itself as the governance layer for AI coding agents. The rebrand is new, but most of the products underneath it shipped earlier this year. Docker Sandboxes are microVMs, each with its own kernel, filesystem, network stack and Docker Engine. Policy is enforced outside the VM, through a default-deny proxy that injects credentials. Cloud sandboxes cost $0.07–$1.12 per hour, and sbx move carries state between laptop and cloud. A Sandbox Kit is an OCI image bundling an agent with its tools and access rules, and audit logs can go to Splunk or Datadog. Upside: real isolation for agents that run shell commands. Downside: mostly a repackaging of existing products, and the governance tier has no public price. For builders: if agents run on employees' machines, a microVM plus an egress proxy is now the baseline to aim for.

NVIDIA · Open data · Document AI · Nov 25

NVIDIA opens 18.9M training examples, a fine-tuning recipe and a DFlash2 speculator for Nemotron 3.5 Parse, its document model

Nemotron 3.5 Parse is NVIDIA's model for turning PDFs, charts and tables into structured text for RAG and agents. NVIDIA has now released three open synthetic datasets, about 18.9 million examples in total, each with images, annotations, generator documentation and training format. The approach is "render and invert": generate many chart and table variants whose ground truth is known, then train the model to reverse the rendering, so every label is exact. NVIDIA says this synthetic data drove most of the gains on charts and tables, and it encourages teams to generate their own variants for specific document types and languages. A fine-tuning recipe comes with the data. For speed, Parse 3.5 already has one-token lookahead (MTP), and the new DFlash2 speculator drafts up to 32 tokens ahead, with about 14 accepted per verification step. On one H200 at concurrency 512, throughput rises from 13.48 pages/s (4.53× Parse 2.0) to 20.44 pages/s (6.86×).

＋ The upsideOpen data plus a recipe lets you adapt the model to your own document types, which rarely happens with document AI. A 6.86× throughput gain makes large-scale ingestion cheap.
− The downsideSynthetic charts are not real scanned documents, so the gap to messy real pages remains. The speed numbers are for H200s at high concurrency, not typical small deployments.
Why it matters for builders
  1. If RAG quality is limited by PDF parsing, try fine-tuning Parse on synthetic variants of your own documents.
  2. Large-draft speculative decoding (32 tokens) is spreading. Check whether your serving stack supports DFlash-style drafters.
  3. "Render and invert" works as a data strategy for any structured output: forms, invoices, diagrams.
  4. Faster ingestion means fresher knowledge bases for support and voice agents.
  5. Measure accuracy on your real documents. Do not rely on throughput numbers alone.

Kubernetes · Patch releases · Nov 25

Kubernetes v1.37.3, v1.36.7 and v1.35.11 ship with Go 1.26.11 and fixes for kubelet user namespaces and scheduler crashes

The release team published three patch releases. The GitHub release listings are timestamped Nov 25 at about 19:55 UTC; the tag itself is from 10:39 UTC. All three are rebuilt with Go 1.26.11, with kube-cross and go-runner bumped and distroless-iptables at v0.9.10. The v1.37.3 changelog fixes several crashes and edge cases. The kubelet now falls back to the default ID range when getsubids is missing and no longer allocates a user-namespace range that ends at the 32-bit limit. Nodes whose subordinate ID ranges reach that limit must shrink them before upgrading. A KCM/kubelet crash with inline vSphere volumes is fixed. The scheduler no longer panics when a Pod is deleted and quickly recreated with the same name. CSINode registration now works when a node is recreated under the same name, so CSI volumes can attach again. No CVEs are listed. Kubernetes 1.35 standard support ends on Dec 28.

＋ The upsideThese are routine but useful fixes. The scheduler and CSINode bugs both hit quickly-churning clusters, such as autoscaled GPU pools and ephemeral agent sandboxes.
− The downsideThe subuid requirement is a real upgrade trap for clusters that run user-namespaced pods. Read the notes before rolling nodes.
Why it matters for builders
  1. If you run agent sandboxes as user-namespaced pods, check /etc/subuid ranges before upgrading.
  2. Fast pod recreation is common in agent and inference autoscaling, so the scheduler fix matters.
  3. Plan the move off 1.35 before Dec 28.
  4. Managed providers (GKE, EKS, AKS) usually ship these patches within days. Watch for the rollout.
  5. Pin your Go-based operators to the same Go patch to avoid TLS or CVE drift.

AWS · Speech-to-text · Voice agents · Nov 25

Amazon Transcribe Turbo previews semantic turn-taking at about 615 ms and runtime hints that lift menu routing from 87% to 97%

AWS released Transcribe Turbo in public preview in US East (Ohio), for both batch and streaming. Streaming covers English, Portuguese, French, Italian, German and Spanish, with about 14% lower relative WER in English and 11% in the other languages, plus formatting accuracy more than 20 points higher. Batch English Turbo is generally available in most regions, and nine more batch languages are in preview with about 16% lower WER. Two new features are aimed at voice agents. Semantic turn-taking decides that a caller has finished from what they said and how they said it (prosody), rather than from silence alone. It responds in about 615 ms with a 5% interruption rate, and the threshold can be tuned. Runtime ASR hints let the app send expected menu options, names and entity types before each turn. On English customer-service data this raised menu-routing accuracy from 87% to 97%. Both features are free and English-only at launch, with more languages promised by the end of December. The base model needs no API change.

＋ The upsideEnd-of-turn detection and per-turn hints are the two biggest causes of bad voice-agent experiences, and AWS now offers both for free inside the STT service itself.
− The downsideThe preview is English-only for the agent features and runs in one region. 615 ms is good but not best in class, and a 5% interruption rate means 1 in 20 turns still gets cut off.
Why it matters for builders
  1. Test semantic endpointing against your VAD-plus-timeout setup. Shorter turn gaps make agents feel smarter.
  2. Send the current IVR menu as hints on every turn. A 10-point routing gain is huge for call deflection.
  3. Tune the interruption threshold per use case: aggressive for quick Q&A, patient for elderly callers or complex intake.
  4. No-code-change accuracy gains make this an easy A/B test for Connect and Transcribe users.
  5. Track whether AWS adds these features to its realtime speech-to-speech stack. That is the next competitive front.
DeepL · Speech translation · Nov 26

DeepL Aure v2: one end-to-end speech-to-speech model that halves translation delay

DeepL announced Aure v2 at its first Unmute Summit in Tokyo. It replaces the three-step pipeline (transcribe, translate, speak) with one end-to-end model that learns when it has heard enough context to start speaking. Median translation delay is 50% lower than the original Aure, released earlier in November. In DeepL's internal tests it beat six competing systems in every language pair, with 32% fewer English–Japanese errors than Gemini 3.5 Live Translate. DeepL Voice minutes grew more than 8× year over year in Q3. Aure v2 turns on automatically in DeepL Voice for online meetings and in-person conversations, and through the DeepL API for Voice. Upside: lower latency without losing accuracy is exactly what real-time interpretation needs. Downside: the benchmarks are internal and the language list is not public. For builders: a single-model streaming translator is a credible base for multilingual voice agents; compare its first-word delay with your ASR→MT→TTS chain.
