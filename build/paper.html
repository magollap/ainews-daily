Anthropic · Claude Code · Developer platform · Nov 23

Claude Ship: Anthropic's agents now review, repair and, under a policy you write, approve pull requests

Anthropic released Claude Ship, which packages three agent roles that cover a pull request from opening to merge. The first, Code Review, is already generally available. It reviews a PR from several angles, challenges its own findings before posting them, sorts what survives into categories, and runs at Quick, Standard or Deep depth set per repository. The second, PR Steward (beta), keeps a PR passing. It fixes failing CI, resolves merge conflicts, and responds to feedback from Code Review, other bots or people. After every push it comments with what it changed and how to undo it. You steer it with an @claude comment and stop it with @claude stop. It never approves or merges anything.

The third, Claude Approvals (beta), is new. It approves a PR only when the PR meets a policy file the team keeps in the repo. Anthropic compares it to a smarter CODEOWNERS file. The policy can use Code Review findings or the team's own natural-language classifiers, and Anthropic advises running it in observe-only mode before making it a required branch check. Developers get a /ship command in Claude Code and the desktop app that pushes the change, opens the PR, reviews it and works on fixes. Branch protection and the developer's own permissions still decide what can merge. Claude Ship is available to Team and Enterprise plans on GitHub. It is not available to organizations using Zero Data Retention, the HIPAA configuration or customer-managed keys. Billing is by tokens: a policy that uses Claude's review triggers a paid Code Review even in observe mode. Eligible Enterprise organizations can claim at least $10K in credits until Jan 15, 2027. Anthropic says the Claude Code team more than doubled its merged PRs from June to September while its revert rate fell more than 40%.

＋ The upsideEach agent has its own role, each change can be undone, the approval policy is stored in the repo where it can be audited, and observe mode lets teams build trust before relying on it. This is the most complete "agent in the merge path" product yet from a frontier lab.
− The downsideLetting an AI approve code moves accountability in ways that auditors and SOC 2 controls haven't caught up with. It is GitHub-only, excludes ZDR and HIPAA customers (who need it most), and token billing even in observe mode makes the cost hard to predict.
Why it matters for builders
  1. Start Approvals in observe mode on low-risk repos such as docs, prompts and evals, and measure how often it agrees with your reviewers.
  2. Write voice-agent prompt and flow changes as PRs, so the same policy gates them.
  3. Set monthly spend caps per repository before turning on PR Steward for busy monorepos.
  4. Keep a human required for changes to billing, auth and telephony routing, whatever the policy allows.
  5. Expect OpenAI's Codex to answer soon. Keep your CI checks vendor-neutral.
OpenAI · ChatGPT · Models · Nov 23

GPT-6.2 reaches the ChatGPT Chat tab: a Sol-based model tuned for everyday chat that handles hard instructions better

The ChatGPT release notes for Nov 23 say a chat-tuned version of GPT-6.2 is rolling out globally in the Chat tab for Plus, Pro, Business and Enterprise. For Enterprise, admins control access. The notes don't mention Free or Go. It is built on GPT-6.2 Sol and tuned for conversation. The models behind Work and Codex, where GPT-6.2 Astra and Sol arrived on Nov 17, stay the same. OpenAI says it handles long, instruction-heavy and web-research requests better, such as comparing hotels on both price and location, and that it is better at offering useful follow-ups, such as offering to alert you when a price drops.

OpenAI's internal numbers against GPT-6: image understanding rises from 47.4% to 71.7%, following instructions on hard prompts from 62.5% to 78.1%, and expert-level tasks at the lowest reasoning setting from 52% to 65%. Internal BrowseComp improves at all four reasoning levels, reaching 64.5% vs 54.4% at Extra high. The system card says compliance in difficult conversations rose from 77–80% to 91–94%, with the largest teen-safety gains in emotional reliance, disordered eating, and age-restricted goods. Some secondary coverage still says 6.2 is "not in Chat yet"; that is now out of date.

＋ The upsideThis is the default model for every paying ChatGPT user, so following instructions better and getting images right more often reaches the largest number of people. The safety-compliance jump is large, and it is documented in a public system card.
− The downsideEvery number comes from internal evals that outsiders can't reproduce. "Proactive follow-ups" can turn into nagging. Free users are left out, and there are now several GPT-6.2 variants that behave differently in different tabs.
Why it matters for builders
  1. Your users' expectations are set by ChatGPT. Better instruction following there raises the bar for your agent.
  2. Benchmark the API GPT-6.2 Sol on your own multi-constraint prompts. Don't assume Chat-tab quality carries over.
  3. Proactive follow-ups ("want me to alert you?") are a UX pattern worth copying in voice agents, with clear opt-in.
  4. The image-understanding gains matter if your support flows take screenshots or photos.
  5. Teen-safety improvements are a reminder to check age-sensitive topics in consumer voice products.
Cisco · OpenAI · Security · Open source · Nov 23

Shirudo: Cisco and OpenAI open-source a system in which agents write signed eBPF "shields" that block exploits on unpatched Linux hosts

Cisco and OpenAI launched Shirudo (Japanese for "shield"), an open-source project under the BSD 2-Clause license, with the BPF programs dual-licensed BSD and GPL. When a vulnerability is disclosed, AI agents trace the vulnerable code path, write a small eBPF program that blocks only the exploit path, and test it against real workloads to make sure normal traffic still gets through. A human must approve every shield. Each shield is cryptographically signed, and hosts verify the signature before loading it. The shield is attached to the running process without a reboot and removed once the real patch ships. The project brings together live protection, AI-assisted investigation, trusted deployment and hardware-backed verification.

In the launch demo, Codex wrote a shield for a "Java4Shell" bug that added an input check to Java's Base64 decoder. The shield was attached to a live Elasticsearch process and rejected the malicious payload. The partners plan to publish tested shields alongside vulnerability disclosures. Cisco CEO Chuck Robbins described Shirudo as a way to "buy time" between disclosure and patch, and Greg Brockman spoke for OpenAI. The code is at github.com/shirudo-dev/shirudo.

＋ The upsideIt shortens the gap between disclosure and protection from days to hours. The design is careful: shields are narrow, signed, approved by a human and removable. Because it is open source, shields can be shared and checked across the industry.
− The downsideAgent-written code running in the kernel is a powerful new attack surface. A bad shield could block real traffic or cause an outage, and the signing keys become a high-value target. It is also a stopgap: teams may use it as an excuse to patch later.
Why it matters for builders
  1. If you run self-hosted voice stacks (SIP gateways, media servers), this could protect them during long patch cycles.
  2. "Agent proposes, human signs, system verifies" is a good template for any high-risk agent action.
  3. Check that your kernels and container hosts support the eBPF features Shirudo needs before counting on it.
  4. Add shield approvals to your on-call runbooks. Otherwise the human step becomes the bottleneck.
  5. It shows OpenAI moving into security infrastructure. Expect Codex security features to follow.
Anthropic · Claude Platform · Enterprise · Nov 23

Enterprise Frontier Safeguards enters public beta: zero data retention plus detection of attacks spread across many requests, with the logs kept in your own bucket

Older zero-data-retention (ZDR) setups on Claude could only run classifiers on one request at a time. Enterprise Frontier Safeguards (EFS), now in public beta, adds monitoring that looks across many requests. That is how it catches attacks split into harmless-looking pieces, such as the multi-agent operation against about 50 organizations that Anthropic described in September. Prompts and responses are written as encrypted "Sealed Safety Data" to the customer's own S3 or GCS bucket under the customer's keys. Neither Anthropic nor the cloud provider keeps a copy, no person at either company reviews it, and it is never used for training. When the monitor finds a risk it opens a Safety Case that contains a case ID, harm category, status and the IDs of flagged transcripts, but no inputs or outputs. Cases are available through storage or an API, so they can be sent to a SIEM.

EFS works on the Claude Platform, Claude Platform on AWS, Amazon Bedrock and Claude on Google Cloud; Microsoft Foundry support is coming. More than 100 companies tested it, including a quarter of the Fortune 100. The same release notes add beta webhooks external_storage.failed and external_storage.recovered, and deprecate Claude Opus 4.5 (claude-opus-4-5-20251101). It retires from the API on Jan 22, 2027, and Anthropic recommends moving to Opus 5.5.

＋ The upsideBanks, health companies and governments no longer have to choose between zero data retention and serious misuse detection. Because the data stays in the customer's bucket, legal reviews get much simpler.
− The downsideThe customer now runs the storage that safety depends on. If the bucket fails, monitoring fails, which is why the new webhooks exist. It is still a beta, and teams on Opus 4.5 have under two months to migrate.
Why it matters for builders
  1. If you sell voice agents to regulated buyers, EFS answers the question "How do you detect abuse without keeping our data?"
  2. Connect the storage webhooks to paging. A silent bucket failure means monitoring has gone dark.
  3. Feed Safety Cases into the same SIEM as your telephony fraud alerts.
  4. Find every claude-opus-4-5 reference in your config now. Jan 22 comes fast over the holidays.
  5. Re-run evaluations on Opus 5.5 before migrating, especially for tool-calling flows.

HYPR · Agent security · Nov 23

HYPR AgentPass gives every AI agent its own identity, a named human supervisor and passkey-approved risky actions

Identity company HYPR launched AgentPass, which treats each AI agent as its own identity rather than letting it borrow a user's session. Every governed agent gets its own credential, linked to a named human supervisor who signs in through Okta, Microsoft Entra or Ping. Agents connect through a governed gateway, start with no access, and can only reach tools the supervisor's role allows. The agent never holds the tool credentials itself. Each request is checked against policies written in plain English, which can allow, block or pause an action for approval, and which can be tested in observe mode first.

Risky actions and new agent connections send a request to the supervisor's phone, approved with a FIDO2 passkey. Every request is logged with the agent, supervisor, policy and a signed approval record, without storing prompts, responses or file contents. AgentPass also finds coding agents such as Claude Code, Codex and Cursor on enrolled Mac and Windows machines, and an authorized user can shut an agent down from a console or a phone. It is available through a private access program, a three-month engagement with no public pricing.

＋ The upsideThis is what CISOs have been asking for: agents with their own identities and credentials, a supervisor who is accountable, and approvals that can't be phished. The audit log leaves out content, which helps with privacy.
− The downsideIt is in private access with no pricing. A proxy in front of every tool call adds latency and a single point of failure. Plain-English policies can be ambiguous, and it is still unclear how they will be tested.
Why it matters for builders
  1. Enterprise buyers will soon ask "Which identity does your agent act as?" Have an answer ready.
  2. Design voice-agent tools so they work behind a gateway, with no long-lived secrets inside the agent.
  3. Passkey approval on a phone fits high-value voice actions such as refunds and account changes.
  4. Watch gateway latency carefully. Every hop costs time in a real-time call.
  5. Logging metadata but not content is a design worth copying for PII-heavy call data.
Polylane · Incident response · Product Hunt #7 · Nov 23

Polylane Swarms sends up to 25 agents to investigate an incident, and a second agent must reproduce each piece of evidence before it counts

Polylane connects to GitHub. When you open a thread and choose "Swarm," agents investigate possible causes in parallel and post their evidence to a shared board. A finding only counts once a second agent reproduces it. A lead agent then combines the confirmed findings into a root cause and a fix, delivered as a pull request. The swarm grows as new leads appear, up to 25 agents including the lead. There is an MCP server so other agents can call it. It is on paid plans only. It reached #7 on Product Hunt on Nov 23 with 135 upvotes.

＋ The upsideRequiring a second agent to reproduce each finding is a practical defense against hallucinated root causes. Running many agents in parallel suits the time pressure of incidents.
− The downsideTwenty-five agents during an outage can cost a lot, and agents debugging production need broad read access. It is an early product, and no accuracy data has been published.
Why it matters for builders
  1. Requiring independent reproduction before accepting a finding is a good pattern for any agent workflow, including QA of voice transcripts.
  2. Call-quality incidents (latency spikes, ASR drift) are a natural use case for parallel hypothesis testing.
  3. Cap swarm size and token budget before connecting it to paging.
  4. An MCP server means your own ops agent can call it as a tool.
  5. Compare it with Claude Ship's PR Steward. The two overlap on "fix PRs."

Aleph Alpha · Cohere · Open weights · Apache 2.0 · Nov 23

Kolibri 1.1: Europe's sovereign MoE uses about 3B active parameters to beat Mistral Small 4 and Nemotron 3 Super, and cuts GPU time per task by 3.4×

Seven weeks after Kolibri 1.0, Aleph Alpha, which is merging with Cohere under the Cohere name, released Kolibri 1.1 under Apache 2.0. It is a German-English mixture-of-experts model with 75B total parameters and about 3.4B active per token. A new sparse-attention design supports up to 1M tokens of context, with 262K recommended for serving. German makes up 21.3% of the pretraining data. The weights take about 77.6 GB, so the model runs on 2× A100/H100 80GB or a single H200/B200/B300.

Most of the gains are in efficiency. Aleph Alpha says it uses 3.4× less GPU time per task (0.208 vs 0.718 modelled GPU-hours per 1,000 tasks), produces 41% fewer output tokens (8,678 vs 14,723), and at 1M context delivers up to 14× the output throughput per GPU while serving 64 concurrent requests per engine instead of 20. Against 1.0, SWE-bench Verified rises from 64.0 to 70.4, Terminal-Bench 2.1 from 25.8 to 35.6, BrowseComp-Plus from 33.1 to 43.9, and AA-Omniscience non-hallucination from 42.1 to 61.1. The biggest jump is AgentDojo prompt-injection resistance, from 30.3 to 99.1. Aleph Alpha's own chart places it on the throughput-versus-German-quality Pareto frontier at 74%. Some larger Qwen and GLM Flash models score higher on German (79–82%), but they are slower.

＋ The upsideIt is a permissively licensed model that fits on one GPU, is strong on agentic coding, and is close to immune to AgentDojo-style prompt injection. It is a credible choice for EU sovereignty requirements.
− The downsideEvery number is vendor-reported. It trails Qwen on tool-calling benchmarks (BFCL, Tau2), which matter most for voice agents. A model that is good at German doesn't help much elsewhere, and the merger with Cohere leaves its long-term roadmap uncertain.
Why it matters for builders
  1. German or EU public-sector voice deployments now have an open model on a single GPU to test.
  2. Fewer output tokens per task means lower latency and cost per turn. Measure it on your own dialogs.
  3. A 99.1 AgentDojo score is worth checking if your agents read untrusted email or web content.
  4. The weaker tool-calling scores argue for keeping a stronger function-calling model in front of it.
  5. Apache 2.0 removes licensing friction for resale and on-prem bundles.
Ant Group · inclusionAI · Open weights · MIT · Nov 23

Ling-3.2-air: a 124B multimodal MoE with 5.5B active parameters more than doubles its predecessor's SWE-bench Pro score, to 58

Ant's inclusionAI lab uploaded Ling-3.2-air to Hugging Face under the MIT license. It is not the LingSante medical model we covered yesterday. It is a natively multimodal mixture-of-experts model that takes text, images and video, with about 124B total and 5.5B active parameters and a 256K context (262,144 tokens). It ships as block-FP8 safetensors, about 129 GB across 13 shards, with day-0 vLLM and SGLang support; the SGLang recipe uses tensor parallelism of 4. Compared with Ling-3.0-flash-VL, SWE-bench Pro rises from 26.4 to 58.28, AutomationBench-AA from 15.7% to 61%, and the GDP.pdf whole-task pass rate from 8.4% to 16%.

＋ The upsideFrontier-level agentic coding with only 5.5B active parameters keeps serving costs low. The MIT license and FP8 weights make it easy to deploy on four GPUs.
− The downsideThe comparison is only against Ant's own previous model, with no head-to-head against Qwen or GLM. Chinese-origin weights face procurement limits in some US sectors.
Why it matters for builders
  1. A 5.5B-active model can answer quickly enough to sit in the reasoning loop of a voice agent.
  2. Native video input makes it possible to build agents that answer spoken questions about screen recordings.
  3. Test SWE-bench-style claims on your own repos before swapping out a paid coding model.
  4. FP8 safetensors plus a ready SGLang recipe means a working endpoint in an afternoon.
  5. Check your customers' policies on Chinese-origin models before shipping it.

6 · DevOps & Kubernetesv1.38 preview · AWS pre-re:Invent · GKE alpha

Kubernetes · kubernetes.io blog · Nov 23

Kubernetes v1.38 preview: the kubelet must get its cgroup driver from the runtime, DRA partitionable GPUs go GA, and a new EvictionRequest API arrives

The v1.38 release team's preview post, ahead of GA on Wednesday, Dec 16 (beta.0 was tagged Nov 6), flags one main upgrade hazard. The kubelet must now get the cgroup driver from the container runtime through the CRI RuntimeConfig RPC (KEP-4033). The kubelet's cgroupDriver setting is deprecated and rejected unless the temporary LegacyCgroupDriverFallback gate is on. If the kubelet can't read the driver after retrying, it exits before the node registers. kubeadm stops defaulting to systemd, and its preflight checks fail on runtimes that lack the RPC. The runtime must therefore be running, and new enough, before the kubelet starts. A second change: with pod-level resources on cgroup v2 nodes using LimitedSwap, swap is now calculated from pod-level memory, so a pod whose memory request equals its limit gets no swap (KEP-2837).

kubectl removes the KUBECTL_REMOTE_COMMAND_WEBSOCKETS and KUBECTL_PORT_FORWARD_WEBSOCKETS opt-outs. It always tries WebSockets first and falls back to SPDY (KEP-4006). kuberc's stable kubectl.config.k8s.io/v1 API accepts only command, not name, in credential-plugin allowlists. cgroup v1 is still being phased out (KEP-5573), and admission webhooks will be permanently stopped from receiving TokenReview and SubjectAccessReview-type virtual resources (KEP-5793). Moving to GA: kuberc, pod-level resources and DRA partitionable devices (KEP-4815), which lets a GPU be advertised both whole and as partitions. New in alpha: an EvictionRequest API (KEP-4563) that lets applications finish their work before a pod is evicted.

＋ The upsideGA partitionable devices make sharing GPUs between inference pods a supported feature. EvictionRequest finally lets stateful and real-time workloads, such as active calls, drain gracefully.
− The downsideThe cgroup-driver change will stop nodes from joining on older containerd or CRI-O versions, which makes upgrades risky. The swap change can silently alter memory behavior for latency-sensitive pods.
Why it matters for builders
  1. Check that your containerd or CRI-O version implements RuntimeConfig before Dec 16, and test node joins in staging.
  2. EvictionRequest is the hook you need to avoid dropping live voice calls during node drains.
  3. DRA partitionable GPUs let you pack several small ASR and TTS models onto one card with proper scheduling.
  4. Update kubeconfig plugin allowlists from name to command.
  5. Check swap settings for pods with request equal to limit if you use LimitedSwap.
